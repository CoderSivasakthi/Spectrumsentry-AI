# SpectrumSentry AI — Communication Monitoring Subsystem (Phase 5)

## 1. Subsystem Overview
Phase 5 introduces a controlled, application-level communication monitoring subsystem for SpectrumSentry AI. It enables real-time telemetry, sequence tracking, latency and jitter estimation, throughput calculation, interruption and recovery detection, and communication health assessment across real local network connections (e.g. Wi-Fi LAN, Ethernet, or mobile hotspots).

```
+------------------------------------+          +------------------------------------+
|              DEVICE A              |          |              DEVICE B              |
|   SpectrumSentry Monitoring Server |          |   SpectrumSentry Test Client       |
|                                    |          |                                    |
|   - Packet Monitor Engine          |  HTTP    |   - Numbered Packet Generator      |
|   - Sequence & Loss Tracker        |<---------|   - Precision Timestamping         |
|   - Latency & Jitter Estimator     |  POST    |   - Configurable Payload & Rate    |
|   - Interruption / Recovery Engine |          |   - Interruption Simulation Pause  |
|   - Health Scoring State Machine   |--------->|   - Local RTT Measurement          |
|   - SQLite Session Persistence     |   ACK    |                                    |
|   - Real-time WebSocket Broadcast  |          |                                    |
+------------------------------------+          +------------------------------------+
```

## 2. Controlled Packet Protocol

SpectrumSentry AI strictly monitors application-level traffic generated by its own client. It does not perform promiscuous packet sniffing or intercept third-party network traffic.

### Packet Payload Structure (`PacketIn`)
```json
{
  "session_id": "client_7d6a6ad045",
  "sequence_number": 123,
  "sender_timestamp": 1729262702.125,
  "payload_size": 1024,
  "payload": "SpectrumSentry-Telemetry-...",
  "protocol_version": "1.0",
  "client_rtt_ms": 3.85
}
```

### Server Acknowledgement (`PacketAck`)
```json
{
  "session_id": "client_7d6a6ad045",
  "sequence_number": 123,
  "server_timestamp": 1729262702.128,
  "status": "CONNECTED",
  "health_score": 100.0,
  "received_packets": 123
}
```

## 3. Session Lifecycle & State Machine

Each monitoring session progresses through an explicit lifecycle managed by `SessionMonitor`:

```
           STARTING
              │
              ▼ (initial packet arrival)
          CONNECTED
          ▲   │   ▲
          │   │   └───────────────────────┐
 (normal) │   │ (loss/lat/jitter warning) │ (stabilized)
          │   ▼                           │
          DEGRADED                    RECOVERING
              │                           ▲
              │ (silence > timeout)       │ (resuming packet)
              └────────► INTERRUPTED ─────┘
                             │
                             ▼ (session stopped)
                          STOPPED
```

- **`STARTING`**: Session created; awaiting initial packet.
- **`CONNECTED`**: Link established, packets arriving within timeout threshold ($<2.0\text{s}$) with normal loss and latency.
- **`DEGRADED`**: Link active, but packet loss ($\ge 5\%$), latency ($\ge 100\text{ ms}$), or jitter ($\ge 30\text{ ms}$) exceed warning thresholds.
- **`INTERRUPTED`**: No packets received for longer than the configured timeout ($\ge 2.0\text{s}$).
- **`RECOVERING`**: Transient state upon receiving the first packet that resumes communication after an interruption.
- **`STOPPED`**: Session explicitly finalized; aggregated statistics persisted to SQLite.

## 4. Metric Formulations

### A. Packet Sequence Tracking & Loss
- **Monotonic Sequence**: Packets are labeled with sequential integers $s = 1, 2, \dots$.
- **Expected Packets**: $\text{expected} = \max(s) - \min(s) + 1$.
- **Lost Packets**: $\text{lost} = \text{expected} - |\mathcal{S}_{\text{received}}|$.
- **Loss Percentage**:
  $$\text{Loss } (\%) = \left( \frac{\text{lost}}{\text{expected}} \right) \times 100$$
- **Out-of-Order & Duplicates**: Out-of-order packets update the received set without falsely registering as lost packets; duplicate sequence numbers are counted separately without inflating the received count.

### B. Round-Trip Latency & Statistics
- Round-Trip Time (RTT) is measured from the client's internal clock:
  $$\text{RTT}_{\text{ms}} = (T_{\text{recv}} - T_{\text{send}}) \times 1000$$
- Summary statistics computed across all received samples:
  - $\text{Min}, \text{Max}, \text{Mean}, \text{Median}, p_{95}, p_{99}$.

### C. Application-Level Jitter
Defined as the mean of absolute differences between consecutive packet latencies:
$$\text{Jitter} = \frac{1}{K - 1} \sum_{i=2}^{K} |\text{Latency}_i - \text{Latency}_{i-1}|$$

### D. Application-Level Throughput
Computed strictly over actual received payload bytes and elapsed session time:
$$\text{Throughput}_{\text{bps}} = \frac{\text{Bytes Received} \times 8}{\Delta t}$$

## 5. Interruption and Recovery Tracking

1. **Interruption Detection**:
   When $\text{current\_time} - \text{last\_packet\_time} > \text{timeout\_seconds}$ (default $2.0\text{s}$), the engine declares an `INTERRUPTION` event, transitions to `INTERRUPTED`, and caps the health score.
2. **Recovery Detection**:
   Upon arrival of the next valid packet, the engine records a `RECOVERY` event, calculates the silence duration:
   $$\text{Duration}_{\text{ms}} = (T_{\text{recovery}} - T_{\text{start}}) \times 1000$$
   increments `recovery_count`, and transitions the session through `RECOVERING` back to `CONNECTED`.

---

## 6. SpectrumSentry Communication Health Score

The health score is a transparent metric normalized from $0.0$ to $100.0$:

- **Base Score**: $100.0$
- **Active Interruption**:
  If the link is currently interrupted, the score is capped at $25.0$ and reduced by cumulative interruption history:
  $$\text{Score} = \max(0.0, 25.0 - (\text{interruption\_count} \times 2.5))$$
- **Continuous Deductions**:
  - **Packet Loss Penalty**: $\min(40.0, \text{Loss } (\%) \times 2.0)$
  - **Latency Penalty**: $\min(25.0, \max(0.0, \text{Avg Latency} - 100) / 4.0)$
  - **Jitter Penalty**: $\min(15.0, \max(0.0, \text{Jitter} - 30) / 2.0)$
  - **Interruption History Penalty**: $\min(20.0, \text{interruption\_count} \times 5.0)$
- **Clamped Range**: Strictly $[0.0, 100.0]$.

## 7. Database Integration

Stored in SQLite at `storage/spectrumsentry.db`:
- **`communication_sessions`**: High-level session aggregates (start/end times, packet counts, loss %, latency percentiles, throughput, interruption count, recovery count, health score, final status).
- **`communication_events`**: Discrete event stream (`STATUS_CHANGE`, `INTERRUPTION`, `RECOVERY`, `PACKET_LOSS`) with sequence numbers and duration.

Packet-level data is tracked in memory for real-time responsiveness and aggregated on session closure.

## 9. Technical Distinction: Signal Domain vs. Communication Domain

SpectrumSentry AI strictly separates its two core telemetry domains:

| Attribute | Domain A: Signal / DSP / AI | Domain B: Communication Monitoring |
|---|---|---|
| **Input Data** | Raw complex baseband I/Q samples | Numbered application-layer packets |
| **Physical Layer** | Synthetic waveforms & AWGN channel | Real OS network socket (Wi-Fi / LAN) |
| **Key Metrics** | SNR, PSD, 23 statistical/spectral features | Packet loss, RTT latency, jitter, throughput |
| **Output** | Modulation (`BPSK`, `QPSK`, `16-QAM`) | Health score, interruption & recovery state |
| **Limitation** | Cannot observe network packet headers | Cannot prove RF-layer jamming or multipath |

A future **Phase 6 Decision Engine** will fuse evidence from both domains to correlate application-level interruptions with physical-layer signal quality.
